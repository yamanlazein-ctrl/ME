## OI-4 — استجابة `POST /api/orders` ترجع `status="open"` رغم أن الحالة الفعلية المحفوظة "available/partially_available"

**لماذا يهم (تأثير منخفض):** الواجهة تنتقل إلى `/orders/:id` بعد الحفظ وتعيد جلب الطلبية (`GET /api/orders/:id`) فتعرض الحالة الصحيحة؛ لكن أي مستهلك لاستجابة الإنشاء مباشرة سيرى حالة قديمة. 

**الإجراء المؤجل (قرار تصميم):** إعادة قراءة الطلبية بعد `applyOrderAvailabilityAtCreation` وإرجاعها في استجابة الإنشاء (أو إرجاع الحالة النهائية من الكائن المحدّث). **لا تعديل كود الآن.**

2. **استلام المطبعة بتكلفة** (`/api/printing/receive` مع `printCostPerKg` > 0) — يكتب `PostgresPrintJobRepository` قيد `Dr مخزون / Cr نقد (cashImpact=out)` (تُحقق حياً: نقص رصيد الليرة 750 ل.س في 2026-08-30).

**الإصلاح المنفَّذ (2026-08-27):** إضافة `assertDayUnlocked` داخل معاملة المسارين:
1. `PostgresInvoiceRepository.create` — عند `paid > 0 && paymentMethod === 'cash'` (يرفُض ويرجّع المعاملة كاملة قبل كتابة قيد النقد).
2. `PostgresPrintJobRepository.receive` — داخل كتلة التكلفة `printCostTotal > 0` (بتاريخ `effectiveDate2`).
+ معالجة `DayLockedError` في `invoiceErrorMessage` (رسالة «اليوم … مغلق») — مسار الطباعة يعيد `e.message` أصلاً.

**دليل التحقق الحي:** فاتورة بيع نقدية بتاريخ 08-27 (مقفول) → `422` «اليوم 2026-08-27 مغلق…»؛ بيع نقدي بتاريخ 08-30 (مفتوح) → `201` (INV-2026-0009). استلام مطبعة بتكلفة بتاريخ 08-27 → `422` «مغلق»؛ بتاريخ 08-30 → `200` (PRT-2026-0004). `tsc --noEmit` نظيف.

**ملاحظة حدود:** القيد اليدوي العام للمحاسب (`writeLedgerUseCase`/`writeMany`) يقبل حقل `cashImpact` نظرياً لكنه أداة تسوية ليست حركة صندوق، وغير معاملاتي؛ تُرك خارج الفحص ويُقيَّم عند الحاجة.

## OI-11 — ملاحظة مستقبلية بعيدة (ليست مهمة حالية): سعر صرف حي عبر API خارجي كمرجع

## OI-12 — ملاحظة تصميم: عرض أرصدة العُملات الأجنبية (أحادي العملة في القائمة/الكشف مقابل متعدد العملات في تقرير الربح)

**الملاحظة (2026-08-27 — بعد إغلاق نمط «رصيد الطرف غير الموحّد»):** أثناء التحقق النهائي لتوحيد أرصدة الأطراف على الأستاذ، تبيّن فرق **عرض** وليس فرق حساب:

| السطح | نطاق العملة |
|---|---|
| قائمة الأطراف `stats.remaining` + كشف الحساب `getBalance` | **أحادي العملة** — رصيد الطرف بعملته الأساسية فقط (`ledger.currency = party.currency`) |
| تقرير الربح (بطاقة الديون `getDebts`) | **متعدد العملات** — يجزّئ المتبقي بعملة كل فاتورة |

**الدليل الحي:** العميل `CUS-2026-0001` (عملته الأساسية SYP) لديه فواتير USD (75+40+6 = 121) وسند قبض USD (500) → رصيد USD سالب (−379 = مخصوم زائد). القائمة/الكشف يعرضان فقط رصيده الـ SYP (74,340)، بينما تقرير الربح يعرض أيضاً رصيد الـ USD. على مستوى النظام: تقرير الربح يعرض ذمم USD مدينة = **118** وذمم USD دائنة = **302.5**، بينما `stats.remaining` (القائمة) بُعد USD = **0** لأن كل الأطراف عملتها الأساسية SYP.

**سبب الدقة:** أرقام العملة الأساسية (SYP) متطابقة 100% بين السطحين (ذمم مدينة 80,840 = 80,840، ذمم دائنة 87,500 = 87,500). الفرق فقط في **تجزئة** العملات الأجنبية الصغيرة لفواتير USD.

**الإجراء المؤجل (قرار تصميم، لا تلمسه الآن):** البتّ لاحقاً — هل (أ) نُبقي القائمة/الكشف أحادي العملة (أبسط، ومطابق لتعريف «رصيد الطرف بعملته»)، أم (ب) نضيف تجزئة متعددة العملات للقائمة/الداشبورد لمطابقة تقرير الربح، أم (ج) تحويل أرصدة العملات الأجنبية لعملة الطرف بقاعدة موحّدة. **لا تعديل كود الآن (قاعدة عدم توسيع النطاق).**
