# T039

`scripts/parity/seed-sync-volume.mjs --hub <url> --invoices N --parties N --out <file>` (also `--pg <hub DB url>` for a disposable cert hub that has no licence row; `--concurrency`):
admin login → enrollment code → `POST /api/sync/enroll` (device kind "seed") → number blocks claimed through `/api/sync/number-blocks/claim` → pushes, through `POST /api/sync/push` with
`X-Sync-Device-Id`, one fabric, one colour, 5 stock rolls, the parties (80% customers / 20% suppliers), then N sale invoices (one deep customer receives 20%, dates spread over four years, USD and SYP
parties) each with one receipt voucher. Unit payloads follow `syncEnqueue.ts` / `enqueueInvoiceCreate` (invoiceId, invoiceNumber, createInput, preAllocated…). It writes `{counts, partyBalances}` (exact integer-cent
arithmetic) and then checks the hub itself: `GET /api/sync/status` `pendingCount`, and every party/currency balance against `GET /api/reports/party-balances` `remaining`.
Run on the cert stack (`CERT_PG_URL=postgresql://postgres:postgres@localhost:5432/postgres E2E_ADMIN_PASSWORD=… CERT_BACKEND_PORT=18080 CERT_UI_PORT=18081 node tests/e2e/cert-stack.mjs`):
`--invoices 1000 --parties 100` → 2,107 units, all `applied`; `[seed] hub pendingCount=0 inbox={"received":2,"applied":2180,"rejected":0,"dead":0} balance mismatches=0` in 37 s (≈ 57 units/s,
so 100,000 invoices ≈ 1 hour). The 2 `received` inbox rows are leftovers of two earlier failed attempts of this very script (a roll status value), not of the final one.
Learned on the way (used by later tasks): roll `status` must be `in_stock`; `rolls.initial_kg` is numeric(12,2); enrollment needs an active licence row (a cert hub has none → the script inserts a test one with `--pg`).
