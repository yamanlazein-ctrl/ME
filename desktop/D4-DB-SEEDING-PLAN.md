# خطة D4: تهيئة وبذر قاعدة البيانات المُجمَّعة (PostgreSQL أحادية الجهاز) — للمراجعة فقط

> **الحالة:** وثيقة تخطيط. لا يوجد أي كود حتى موافقة مشتركة على هذه الخطة وخطة الترخيص.
> **الهدف:** تطبيق Windows يعمل offline بالكامل — قاعدة PostgreSQL محلية تُشحن مع المثبّت،
> تُهيَّأ تلقائياً عند أول إقلاع دون أي إعداد يدوي.

---

## 0. حقائق من الكود (دليل، لا تخمين)

- `backend/src/scripts/seed.ts`: ينشئ tenant افتراضياً **بمعرّف عشوائي** (`defaultRandom()`) — لا يثبّت `407fccfc-...`.
- لكن كل تسجيلات الدخول/الاختبارات والواجهة تتوقع `tenantId = 407fccfc-ba89-41c5-b5b9-ddb2c4f385d9`
  (عبر `VITE_DEFAULT_TENANT_ID` في `.env.example`، وكل سيناريوهات `tests/e2e` تمرّره صراحة مع `admin123`).
  ⇒ **فجوة:** البذر الحالي لن ينتج المعرّف الذي يتوقعه التطبيق. يجب تثبيت المعرّف في خطوة البذر.
- `seed.ts` **لا يكتب إلى جدول `secrets`** (يُدرج tenants + users فقط) ⇒ يتوافق مع شرط D3-1 (جدول أسرار فارغ).
- `backend/drizzle.config.ts`: `schema: ./src/infrastructure/orm/schemas/*.table.ts`، `out: ./src/infrastructure/orm/migrations`، dialect postgresql.
  سكربتات: `db:migrate` (drizzle-kit migrate) و`db:push:scratch` (drizzle-kit push).
- `backend/src/infrastructure/config/env.ts:17`: `DATABASE_URL` **إلزامي** (`z.string().url()`) ⇒ الـsidecar يجب يحقنه.
- لا يوجد أي أثر لـ PostgreSQL/initdb/seed داخل `desktop/` حالياً ⇒ الآلية غائبة بالكامل ويجب بناؤها هنا.

## 1. النهج المقترح: تجميع PostgreSQL + pgdata مبنية مسبقاً

### 1.1 ما يُشحن مع المثبّت
1. **ثنائيات PostgreSQL لـ Windows** (مجلد `bin/`, `lib/`, `share/`) من توزيع EDB "binaries"
   (مثلاً `postgresql-16.x-windows-x64-binaries.zip`). نثبّت إصداراً محدداً (مثلاً 16.x) ونثبته.
   - `pg` (node-postgres) متسامح مع إصدار الخادم؛ 16.x آمن وعريض التوافق.
2. **مجلد `pgdata` مبني مسبقاً** يحتوي schema + البذر + رمز الترخيص المخبوز (انظر §2)،
   مع `pg_hba.conf` مضبوط على `trust` لـ `127.0.0.1` (قاعدة محلية فقط — بلا كلمة مرور).
3. ملفات الـbackend المبنية + واجهة SSR (خطوات لاحقة).

> **بديل (B) أكثر قابلية للنقل بين إصدارات PG:** شحن `pg_dump` archive وتشغيل
> `initdb` + `pg_restore` عند أول إقلاع. أبطأ في أول إقلاع ويتطلب مهاجرات وقت التشغيل.
> **نوصي بالنهج (A)** لإقلاع أسرع و offline صارم.

### 1.2 خطوات آلة البناء (pipeline "الخبز") — كلها على جهاز المطوّر
1. فك ثنائيات PG إلى مجلد مؤقت؛ شغّل `initdb.exe -D <build_pgdata> -U postgres --auth=trust -E UTF8`.
2. شغّل `postgres.exe -D <build_pgdata> -p <PORT>` ثم `createdb erp`.
   - **منفذ مخصّص:** نستخدم منفذاً غير افتراضي (مثلاً `54329`) لتفادي التعارض مع PG محلية موجودة لدى العميل.
     يُحرق في `DATABASE_URL` المجمّع.
3. **تطبيق المخطط:** `DATABASE_URL=postgresql://postgres@localhost:<PORT>/erp npm run db:migrate`.
   - ⚠ تحقّق: إن فشل `db:migrate` على المهاجرة 0001 (سياسة RLS كما لوحظ سابقاً)، نستخدم
     `npm run db:push:scratch` لبناء DB المجمّعة فقط، ونسجّل الأمر الدقيق.
4. **البذر مع تثبيت المعرّف:** نعدّل `seed.ts` لاحترام `SEED_TENANT_ID` (افتراضي المعرّف الثابت
   `407fccfc-ba89-41c5-b5b9-ddb2c4f385d9`) وإلا يولّد عشوائياً. ولإنتاج كلمة مدير **معلومة**
   للعميل، نضيف `SEED_ADMIN_PASSWORD` (افتراضي `admin123` للنسخة المكتبية، أو توليد يُعرض عند أول إقلاع).
   ⇒ هذا تعديل كود بسيط في `seed.ts` (جزء من تنفيذ D4).
5. **خبز الترخيص (الخيار د):** تشغيل `bake-desktop-license.mjs` (معرّف في خطة الترخيص) يُدرج صف
   `licenses` + الرمز الموقّع (صلاحية ~100 سنة) مرتبطاً بالـtenant الافتراضي.
6. **إفراغ جدول الأسرار (D3-1):** `DELETE FROM secrets WHERE tenant_id = '407fccfc-...';`
   (أمانة إضافية — البذر أصلاً لا يكتب أسراراً).
7. أوقف `postgres`، احزم `<build_pgdata>` كـ `pgdata` المجمّع.

### 1.3 تغليف المثبّت (Tauri)
- `tauri.conf.json` → `bundle.resources`: يشمل مجلد ثنائيات PG ومجلد `pgdata` المجمّع.
- لا حاجة لـ `externalBin` لمجلد؛ `resources` يكفي. الـsidecar القابل للتنفيذ هو `postgres.exe`
  (يُستدعى من مجلد الموارد، ليس كـ externalBin منفصل).

## 2. أوركسترايشن أول إقلاع (Rust sidecar — نظرة عامة؛ التنفيذ الكامل في خطوات 6–12)

في `desktop/src-tauri/src/main.rs` عند الإقلاع (قبل فتح النافذة **وقبل أي عمل على قاعدة البيانات**):
0. **فحص/كتابة بصمة الجهاز (DPAPI) — البوابة الأولى المطلقة:** اقرأ/أنشئ `device-binding.dat`
   (انظر `LICENSE-ACTIVATION-PLAN.md` §4). إن فشل فك التشفير (جهاز/مستخدم آخر) أو اختلفت البصمة
   ⇒ **ارفض الإقلاع فوراً دون لمس قاعدة البيانات إطلاقاً**. هذا يضمن أن نسخ مجلد البيانات إلى جهاز
   آخر يُرفض قبل أي نسخ `pgdata` أو تشغيل `postgres`.
1. حلّ مسار الموارد (ثنائيات PG) ومسار بيانات التطبيق `%APPDATA%/motard-erp/`.
2. إن غاب `%APPDATA%/motard-erp/pgdata/PG_VERSION` ⇒ انسخ `pgdata` المجمّع إلى بيانات التطبيق
   (مرة واحدة). للنهج (B) بدلاً من ذلك: `initdb` + `pg_restore`.
3. شغّل `postgres.exe -D <pgdata> -p <PORT> -c listen_addresses=127.0.0.1 -c unix_socket_directories=''`
   كعملية ابن؛ التقط stdout/stderr إلى سجلّ؛ أدر دورة حياتها.
4. انتظر حتى يقبل `127.0.0.1:<PORT>` الاتصال (استطلاع مع مهلة).
5. حقن `DATABASE_URL=postgresql://postgres@127.0.0.1:<PORT>/erp` + (`DESKTOP_DEPLOY=true`,
   `PORT=8080`، `JWT_SECRET`/`APP_MASTER_KEY` من مخزن D3، `LICENSE_SIGNING_PUBLIC_KEY`)
   في بيئة الـbackend sidecar.
6. ثم شغّل backend + واجهة SSR (خطوات لاحقة).
7. عند إغلاق النافذة/خروج التطبيق ⇒ أنهِ `postgres` (وغيره) بنعومة (لا عمليات يتيمة).

## 3. المخاطر

- **R1 (إصدار PG):** مجلد `pgdata` المبني مسبقاً مقفل بإصدار ثنائيات PG المجمّعة — يجب تطابقهما تماماً.
- **R2 (معرّف tenant):** `seed.ts` يولّد معرّفاً عشوائياً؛ يجب تثبيته على `407fccfc-...` وإلا فشل تسجيل الدخول. (تعديل كود في seed.ts.)
- **R3 (db:migrate مقابل db:push):** تحقّق أيهما يعمل فعلياً على آلة البناء؛ وثّق الأمر الناجح.
- **R4 (أمان pg_hba — تحليل مُوثّق):** القاعدة مربوطة بـ `listen_addresses=127.0.0.1` فقط
  (غير قابلة للوصول عبر الشبكة). مع `trust`، أي عملية **محلية** يمكنها الاتصال بصلاحيات `postgres`.
  - *لماذا trust مقبول لنموذج single-device:* الـDPAPI المستخدم لبصمة الجهاز بنطاق **CurrentUser**
    قابل للفك بأي عملية تعمل بنفس المستخدم ⇒ مصادقة SCRAM بكلمة مخزّنة في DPAPI **لا تمنع** برمجيات
    محلية تعمل بنفس المستخدم. ومدير النظام (admin) يستطيع قراءة ملفات `pgdata` على القرص مباشرةً
    بغض النظر عن المصادقة. لذا SCRAM+DPAPI لا يغلق التهديدَين الرئيسيّين (نفس المستخدم / admin)،
    وإنما يضيف فقط دفاعاً ضد: (أ) مستخدم محلي منخفض الصلاحية، (ب) تسريب كلمة ثابتة من حزمة المثبّت.
    التكلفة: تدوير كلمة عشوائية عند أول إقلاع + إعادة كتابة `pg_hba.conf` + إعادة تحميل postgres
    (تعقيد غير مبرّر للنموذج المغلق). **القرار المقترح: `trust` على 127.0.0.1 كمخاطرة موثّقة.**
  - *تحسين بسيط بلا تعقيد SCRAM:* إن أردت تقليل الضرر عند اتصال عملية محلية، أنشئ دوراً بصلاحيات
    محدودة للتطبيق (وليس superuser) واترك `postgres` مقيّداً — يبقى `trust` لكن بأثر أصغر.
  - *تحسين اختياري أقوى (opt-in):* SCRAM-SHA-256 بكلمة عشوائية لكل تثبيت تُولَّد عند أول إقلاع
    وتُخزَّن في مخزن D3، مع خطوة تدوير لمرة واحدة (`ALTER ROLE postgres PASSWORD ...` عبر trust
    مؤقت ثم تبديل pg_hba إلى scram وإعادة التحميل). يُطبَّق فقط إن رغبت بالدفاع ضد المستخدمين
    منخفضي الصلاحية وتسريب الحزمة.
- **R5 (الحجم):** ثنائيات PG ~100–200MB + pgdata؛ المثبّت بضع مئات MB. مقبول لتطبيق ERP مكتفٍ ذاتياً.
- **R6 (بطء النسخ أول مرة):** نسخ pgdata على قرص HDD قد يستغرق ثوانٍ؛ مقبول.
- **R7 (أسرار فارغة D3-1):** تُفرض بخطوة `DELETE` في البايبلاين.
- **R8 (كلمة مدير معلومة):** البذر يجب ينتج كلمة مدير معلومة للعميل (SEED_ADMIN_PASSWORD) لا عشوائية
  تُطبع فقط، وإلا لا يمكن للعميل تسجيل الدخول. قرار مطلوب (admin123 vs توليد يُعرض بالمعالج).
- **R9 (تعارض المنفذ):** استخدام منفذ مخصّص (54329) يتفادى صدام PG محلية عند العميل.

## 4. خطوات التحقق (عند التنفيذ)

1. آلة البناء: بايبلاين الخبز ينتج `pgdata`؛ تشغيل postgres منه؛ الإقلاع بـ `DESKTOP_DEPLOY=true`
   يتصل بنجاح؛ تسجيل الدخول `admin@erp.local` يعمل؛ `secrets` فارغ؛ صف `licenses` موجود؛ الرمز
   يتحقق بالمفتاح العام؛ لا مفتاح خاص في `.env` المجمّع.
2. VM نظيف: تثبيت MSI؛ أول إقلاع ينسخ pgdata؛ postgres يشتغل؛ التطبيق يعمل offline بالكامل؛
   لا عمليات يتيمة بعد الإغلاق.
